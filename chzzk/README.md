# CHZZK and Chrome integration handoff

No CHZZK adapter or Chrome extension is installed yet. The relay remains generic. On 2026-09-23, the Linux server reached the CHZZK website but `api.chzzk.naver.com` timed out. No real CHZZK playback, CDN redirect, token expiry, or LL-HLS behavior has been verified.

## Playback information

The [current Streamlink CHZZK implementation](https://github.com/streamlink/streamlink/blob/master/src/streamlink/plugins/chzzk.py) reads a channel's `live-detail` response, parses `livePlaybackJson`, and selects an HLS media path. It has a separate `live-playback-json` call in some cases and adds a token derived from the manifest URL to certain `.m4v` segment URLs. This is evidence of possible compatibility requirements, not proof that this relay needs those changes. The [official CHZZK Open API live list](https://chzzk.gitbook.io/chzzk/chzzk-api/live) uses client authentication and is not itself a playback URL source for this project.

When the API is reachable, test a public live channel without Naver account credentials first. Extract only an HLS `media[].path`, pass it as `upstream_url` to `POST /api/session`, and check the original manifest, nested manifests, multiple successive video/audio segments, CDN redirects, and `ffprobe`/`ffmpeg` through the relay. Record HTTP status, content type, codec, and request counts without recording signed URLs or tokens. Check expiration by observing whether a fresh `live-detail` or `live-playback-json` call is needed. If the server cannot get a valid URL, the extension can supply a temporary playback URL from its own authorized browser context and create a new session on expiry. Do not send Naver cookies to the relay.

## Windows Chrome phase

1. Inspect the normal CHZZK page in Chrome DevTools before playback and after stopping. Identify the player, HLS manifests, grid/P2P process or loopback traffic, and any WebRTC or upload traffic. Measure both download and upload after stop.
2. Determine a way to prevent the original player from starting its grid/P2P path **before** relayed playback begins. Possible approaches include an early main-world hook into the player initialization, replacing the player component while preserving chat/navigation, or narrow `declarativeNetRequest` rules to block identified grid requests. Test each against page updates and verify that no original video requests continue. A visual overlay alone is insufficient. [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) use an isolated world by default; main-world injection shares page JavaScript and is subject to page CSP. [Declarative Net Request](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest) operates on network requests but may not cover a native helper, WebRTC, or all request types.
3. Let the extension background service worker create/delete relay sessions and hold the relay API token. [Chrome's cross-origin rules](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests) distinguish extension-context requests from content-script requests. Give the extension permission only for the CHZZK page and private relay endpoint. Validate any page-to-extension message; never expose a generic authenticated fetch bridge.
4. Test the actual rendering path. Chrome desktop does not guarantee native playback of every HLS codec/container combination. A page-side HLS player may use Media Source Extensions and fetch manifests/segments, requiring relay CORS for `https://chzzk.naver.com`; the page CSP and HTTPS mixed-content rules may also matter. Confirm the chosen player consumes the relay URL and that audio/video remain synchronized through quality changes and token refresh.
5. On pause, navigation, tab close, player error, and extension shutdown, stop the player fetches and issue `DELETE /api/session/<id>`. The server's disconnect cancellation and 30-second idle expiry are fallbacks. Verify zero grid/P2P traffic on Windows and zero relay sessions/upstream requests on Linux afterward.

The decisive acceptance test is simultaneous: the normal site still handles login/chat/navigation, relayed video and audio play for several minutes, and stopping playback leaves no CHZZK grid/P2P download or upload on Windows and no media transfer on Linux. None of those browser-side claims have been verified yet.
